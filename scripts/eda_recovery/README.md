# 嘉立创原生覆铜独立试验

只操作 `eda-recovery-probe` 试验工程。飞鼠原成果和收尾工程保持原样。本目录脚本不删除、修改已有焊盘、导线、板框或覆铜边框，不修改客户端程序。

`init_probe.js` 创建 25.4 × 20.32 mm 板框，以及地网络和信号网络各两个焊盘。`pour_probe.js` 创建名为 `RECOVERY_GND_TOP` 的新顶层地覆铜，范围为 `(20,20)` 到 `(980,780)` 密耳，距板框 20 密耳；随后依次请求重建、读取单个覆铜区域、读取全部覆铜填充图元和编号。编号和实际区域路径独立保存到返回对象，重建异常会保留错误和调用栈，不会中止后续只读检查。

由根代理通过已配置的官方接口执行脚本，并将返回对象写入本试验工作树的独立输出目录。创建仅执行一次；再次传入 `inspectOnly: true` 时仅重新读取填充数据，不重建、不保存。不应在试验覆铜已存在时再次运行创建模式。

判断时同时检查 `after.readsSucceeded`、`matchingRegions`、`fillCount` 和真实导出文件。`hasFillData` 表示软件接口读到了关联的填充数据；尚不能证明数据已写入磁盘或制板文件，也不能证明覆铜满足连接、间距和制造要求。保存结果另列于 `save`，重新打开工程及铜层导出需另行核对。

## 已知接口证据

2026-10-05 只读核对：官方[重建覆铜文档](https://prodocs.lceda.cn/cn/api/reference/pro-api.ipcb_primitivepour.rebuildcopperregion.html)的示例捕获了“纯 API 创建的覆铜上重建会报内部错误”。直接 HTTP 读取和网页工具均可读取该段，不来自项目笔记。该提示说明已知环境可能失败，不能据此认定所有窗口或所有版本均失败。

本机接口包 `E:\各种软件\嘉立创专业版4\resources\app\assets\pro-api\0.3.44.a22d1ca5\api.js` 中，`rebuildCopperRegion()` 把远程返回值交给 `C3()`，后者直接访问 `e.length`；返回 `undefined` 会抛出当前错误。`getCopperRegion()` 使用相同转换函数，因此还要独立读 `pcb_PrimitivePoured.getAll()` 和 `getAllPrimitiveId()`。这定位了错误发生的位置，尚不能确定远程返回值为何为空，也不能据此判断底层是否生成填充。

客户端 `pro-pcb\4.1.57.3c4dbafd\js\pcb.js` 的原生重建会创建 `pcb-worker.js` 计算任务，执行 `pourDocument` 并写回铜区域。若小矩形实验仍失败，应分别保留接口异常、独立区域读数和导出铜层，再比较现有原生重建命令执行后的只读结果。不得把手工填充图形冒充原生覆铜恢复，也不把试验结果直接写回飞鼠设计。

## 公开窗口入口核对

`pour_menu_probe.js` 仅在当前活动文档属于独立试验工程时，通过官方 `sys_Window.openUI('RebuildAllCopperArea')` 试验窗口入口，并独立读取填充数据，不保存、不调用私有消息。此脚本尚未由本代理执行。

只读客户端代码显示 `RebuildAllCopperArea` 是 Shift+B 对应的快捷键标识。PCB 会把它转换成内部命令 `Rebuild All Copper Area`，后者触发原生重建。但窗口入口的 `ht()` → `Od()` 菜单分发中没有该快捷键标识的处理分支；`Od()` 对无括号的未知命令直接结束。因此窗口入口可能静默返回且没有重建行为，不应把“调用返回”记录为恢复成功。公开窗口入口参数的[官方说明](https://prodocs.lceda.cn/cn/api/reference/pro-api.sys_window.openui.html)也提示参数没有额外文档且可能随版本变化。

证据位置：当前 `pro-ui\4.1.68.3635b9da\js\ui.js` 字符偏移 `4966994` 是快捷键映射，`9853503` 是公开窗口入口，`18414148` 是 `ht()`，`11166813` 是 `Od()`；`pro-pcb\4.1.57.3c4dbafd\js\pcb.js` 字符偏移 `5073391` 是快捷键命令转换，`9242960` 是原生重建执行分支。上述位置属于当前文件版本，版本更新后需重新检索。

## 2026-10-05 的实际对照结果与边界

根代理已执行可见窗口试验，`.logs/pour-visible.json` 显示创建成功，重建在 `C3()` 抛出读取 `undefined.length` 的错误；独立读取填充编号、对象和保存后的数据均未得到填铜。这次已经实证没有生成填充，不只是一条包装层异常。

测试板的默认 `COPPER` 规则已经存在，多层焊盘采用热焊连接，连接间隙与线宽均为 10 密耳。覆铜存盘数据为顶层 `GND`、实心填充、细度 8、保留孤岛否，矩形范围正确。接口创建的 `hHA()` 与原生界面创建都从 `ld.fillComponent` 读取同一组默认配置并创建 `ri` 对象，没有发现接口漏掉独立热焊默认字段的证据。公开覆铜修改方法不提供热焊规则字段；不要编造 `Thermal` 等额外参数。

根代理在另一新无窗口会话中通过菜单兼容入口读到了两条线；同一会话的 `.logs/pour-headless.json` 则在创建覆铜时失败，而且保存返回 `false`，耗时 87 ms。这与可见窗口的重建失败发生在不同阶段。客户端创建入口除了当前活动标签的 PCB/封装类型，还检查标签、项目、模块任务或协作签出的只读权限；读取填充/线图元没有相同写权限检查。因此读取正常不能证明创建和保存权限正常。接口包又会把真实创建错误替换成笼统的“参数不正确”，目前尚不能断言是几何问题。

原失败证据保留。`pour_probe.js` 已改为仅核对当前活动 PCB，不主动重新打开文档，以排除再次激活造成的状态差异；返回对象增加当前文档属性。本探针旧版调用 `openDocument()` 后立即继续，属于历史试验尚需排除的时序变量。

追加发现：根代理同事核实自动布线默认勾选“展示迭代结果”，上述两条线可能处于迭代预览，从而使当前 PCB 只读；这个解释仍在验证，不能先把预览读数当作已保存布线。用户已被告知暂缓快捷键对照，根代理正在验证关闭预览的项目设置。

在确认迭代预览已经结束且测试板可写后，若公开接口仍失败，可让用户仅在独立试验板画布按一次 Shift+B，再由根代理只读核对填充及导出。专业版[铺铜区域说明](https://prodocs.lceda.cn/cn/pcb/place-copper-region/index.html)明确该快捷键重建全部铺铜，包括内电层；必须确保当前窗口为独立测试工程，不能误在飞鼠原工程执行。没有通过这个对照前，不宣称原生覆铜恢复。

## 2026-10-05 更正：试验矩形原生坐标方向

前面的“矩形范围正确”判断有误，必须更正。旧探针使用 `['R',20,20,960,760,0,0]`，本代理此前依据接口包通用离散函数误判其覆盖 `y=20～780`。原生 PCB 矩形实际以左上点为起点，向负 Y 方向延伸高度，所以旧探针覆盖的是 `x=20～980、y=-740～20`。板框是 `y=0～800`，地焊盘中心在 `y=200`，两者没有被旧覆铜覆盖；板框裁剪后剩余窄区还可能被“删除孤岛”正常移除。

证据在当前客户端 `pro-pcb\4.1.57.3c4dbafd\js\pcb.js`：`ab()`（字符偏移 `11243607`）直接把矩形坐标和宽高传入原生矩形；`An`（字符偏移 `4633068`）定义 `leftUp=start`、`leftLow=(start.x,start.y-height)`、`rightLow=(start.x+width,start.y-height)`。热焊的 `getPads()` 在图元空间索引中按同网及图层查询焊盘，没有要求焊盘必须属于器件，因此不能把独立焊盘本身直接判为无效。

现已把独立探针改为显式闭合四角 `[20,20,'L',980,20,980,780,20,780,20,20]`，目标范围明确为 `x=20～980、y=20～780`；输出另保留 `pourSource` 供核查。原失败日志保留，但旧几何的空填充和无填铜导出不能用于证明原生铺铜算法失败。需要根代理在正确范围、可写状态下重新对照；本代理仅修改探针及本说明，未执行会话、未修改飞鼠设计。

## 2026-10-05 最终复测：纯公开接口无窗口覆铜成功

根代理已在可写的独立试验工程，将错误 R 矩形修正为上述闭合 L 四角后重测。`.logs/repair-pour-headless.json` 显示重建返回真实区域，得到 9 条填充路径（1 个铜面、8 条热焊连接线），异常列表为空、保存成功，设计规则检查结果为空；存盘数据也有 9 条真实路径。根代理导出的修正后顶层制板文件包含 1 组 `G36/G37` 铜面区域指令，而旧错误几何为 0 组。

根代理关闭自己创建的试验会话并重新打开后，`.logs/verify-headless-final.json` 显示地和信号两组焊盘分别有真实连接、`allDirectConnectionsPresent=true`，9 条填充路径仍存在，设计规则检查仍为空，证明成果已经保存并能重新读取。

随后根代理在另一全新四焊盘工程直接执行修正后的公开创建、重建、保存流程。`.logs/pure-create-pour-corrected.json` 显示 `created=true`、重建和区域读取成功、`fillCount=9`、异常列表为空、保存成功；`.logs/disk-direct-pour.json` 再次从磁盘读取到正确闭合范围和 9 条填充路径。这排除了只修旧对象才成功的情况，证明本机当前版本在正确几何、可写状态下可通过纯公开接口进行无窗口原生覆铜。

此次收尾必须保留前述几何误判更正：旧 R 矩形实际延伸到 `y=-740`，因此其空填充不能归因于原生算法失败。先前不可写状态下的错误日志也保留，不能与本次可写复测混为同一条件。结论范围是上述独立小板、本机当前客户端及相应接口版本；没有据此宣称原 AI 在复杂飞鼠板上遇到的全部历史异常已根治，也没有改变复杂飞鼠板原成果和设计。
