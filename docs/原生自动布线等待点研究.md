# 原生自动布线等待点研究

本次研究只读安装资源和官方资料；没有启动、关闭或切换会话，没有修改软件或枪型飞鼠工程。动态试验由主代理在独立 `eda-recovery-probe` 工程执行。

## 已确认的本地代码链

安装目录 `resources/app/editor.ini` 指向 `pro-versions/4.1.66.1b2cf7e4/editor.js`，该版本清单同时加载 `pro-api/0.3.44.a22d1ca5` 和 `pro-ui/4.1.68.3635b9da`。

真实运行的 `pro-api/.../api.js` 中，`PCB_Document.autoRouting` 组装参数后请求 `extensionApi.PCB_Document.autoRouting`。接口参数为 `RoutingNets`，不是旧示例中的 `nets`。公开参数只支持网络范围、拐角、保留或移除旧导线、优化优先级、图层和忽略网络；没有后台模式、布线引擎或弹窗确认参数。

本机 `pro-ui/.../js/ui.js` 的 `PCB_Document` 服务注册表包含导入、保存、清除布线等方法，却没有 `autoRouting` 或 `autoLayout`；注册函数只遍历表中方法。对应通信实现的请求默认超时为零，即没有接收服务时，响应 Promise（异步结果）可以一直未完成。这是此前“11 分钟、计算进程空闲、接口不返回”的首要等待点疑点：请求可能还没有进入布线引擎。

目前没有证据表明它正在等待登录、收费服务或设置确认框。静态代码不能单独证明运行时加载状态，仍需有界对照试验。

## 独立试验脚本

`scripts/eda_recovery/autoroute_probe.js` 先核对工程友好名称及当前 PCB 文档归属，读取图元计数，只对 `GND` 调用公开接口，保留已有导线和过孔，速度优先，允许顶层、底层。主代理先建立简单板框与两枚未连通的 `GND` 焊盘；脚本不创建或删除图元，也不自动保存。

等待原生接口最多 12 秒，然后记录返回、拒绝或仍未响应，重新读取顶层导线、底层导线和过孔数。12 秒约束布线调用的等待，不是进程强制终止；前后只读计数所需时间另计。`Promise.race` 不能取消原生任务，超时后应只在该实验工程继续观察，不把同一待处理会话改开为正式工程。

示例调用，由主代理填写它自己的试验会话编号：

```powershell

  -- invoke --session 试验会话编号 --ext-uuid eda --timeout 25000
```

最小对照：先在后台试验会话执行，再在可见试验会话执行同一探针；若均不返回，再请用户在测试工程使用普通“布线→自动布线→所有网络”菜单，观察是否能真正生成导线。若菜单能运行而公开接口均无响应，证据指向接口桥接缺口；如果菜单也不能运行，才继续查看实际界面和布线引擎状态。不能据此要求用户先重新登录或改变全局设置。

尚未执行以上试验，也没有修补安装资源。优先保留当前成果并向官方报告版本接口接收端缺失；是否升级到修复版本须先核对官方发行和接口实现，不能靠无限增加超时解决缺少接收服务的问题。

## 2026-10-05 追加：菜单路径及版本相关兼容入口

继续只读追踪本机安装资源，确认菜单“布线→自动布线→所有网络”使用命令名 `autoRouting(ALL_NETS)`。在 `pro-ui/4.1.68.3635b9da/js/ui.js` 中，菜单处理程序调用 `Y_i(0)`，读取当前 PCB 的布线设置和活动图层后发布 `pcb/autoRouting`。单独命令 `auto-routing` 只打开设置，不能当作开始布线。

`pro-pcb/4.1.57.3c4dbafd/js/pcb.js` 接收此菜单消息后调用原生 `autoRouting`。实际算法启动链为：菜单消息 → 活动 PCB 检查 → 板框及间距检查 → 生成布线输入 → 本地 `pcb-router-worker.js`。速度优先时派发 `pangolin/autoRouting_wasm`，完成率优先时派发 `pangolin/autoRoutingJR`。这些名称仅作故障证据，本试验不调用内部消息或工作线程接口。

已确认的前置阻断条件包括：目标必须是活动 PCB／PCB 模块；必须存在有效闭合板框；板框与铜区、走线的间距规则必须大于零。该入口代码未发现登录或云端服务确认步骤，因此不应仅凭长时间等待要求用户重新登录。静态阅读也不能证明所有运行时问题均已排除。

此调用没有在本次子任务中执行。它读取已有设置，且返回仅表示命令处理结束，不是布线完成。开启迭代展示时还要确认结果已应用，再依据新增导线、过孔及设计规则检查评价是否完成。

必须保留接口边界：[官方 openUI 文档](https://prodocs.lceda.cn/cn/api/reference/pro-api.sys_window.openui.html) 将其备注为“非公开接口使用提醒”，不保证名称及参数的版本兼容性；未知名称可能静默无效。它是官方文档列出的兼容入口，不能写成稳定的专用自动布线接口，也不能据其有效声称 `pcb_Document.autoRouting` 已修复。若不采用此兼容入口，用户在小测试工程手动执行普通菜单即可作同样对照。

[官方快捷键表](https://prodocs.lceda.cn/cn/introduction/hotkeys/index.html) 没有给出自动布线的默认快捷键。菜单带自定义快捷键标识，但本次未查询或改动用户实际绑定，不假定某个组合键可启动自动布线。

## 2026-10-05 追加：预览只读、保存失败及交付边界修正

后续主代理在可见和无窗口两份独立小板都读取到 2 段真实网络导线。`.logs/verify-visible-routing.json`、`.logs/verify-headless-routing.json` 的连接检查均确认两对焊盘分别连接，设计规则检查均为 `[]`；但两份记录的 `save` 都是 `false`。无窗口小板 `.logs/pour-headless.json` 的覆铜创建失败，随后保存也为 `false`。磁盘 `pcb/eda-recovery-probe-headless/pcb/PCB1.epcb2` 未保存本次预览产生的导线。因此，此前菜单试验只证明算法及画布结果可运行，**尚不能声称能持续自动完成制造导出，或已恢复正式工程的完整原生自动布线流程**。

[官方迭代说明](https://prodocs.lceda.cn/cn/pcb/route-auto-routing/) 区分画布预览与应用：展示迭代结果默认开启，用户选定迭代后应用才更新 PCB，关闭迭代面板会恢复布线前状态；关闭展示时才直接应用最后结果。画布读取到真实图元及零项规则错误，仍不足以证明结果已保存。

本机代码给出一致的只读原因链（只读研究，未调用这些内部方法）：

1. `ui.js` 约 18460178 的菜单 `Y_i(0)` 读取当前标签配置；若 `isDisplay` 为真，先启用迭代面板。
2. `ui.js` 约 7845045 的面板 `setTabActive()` 显式设置 `A.isAutoRouterMode=true`、`Bi.setIsProjectReadOnly(true,当前工程ID)`。面板关闭才重新计算正常编辑权限。
3. `ui.js` 约 19793186 的覆铜创建服务先调用 `$n()`；`getIframeDisableStatusPanelPcb` 约 17498847 把工程只读判为禁止编辑。服务返回 `null`，外层公开接口会产生通用“可能是参数不正确”的创建错误。这不等于实际已证明多边形参数错误，也不等于无窗口覆铜引擎失败。
4. 保存流程 `EMe.checkPcb` 约 17512824 调用 `zN(tabid,docType,true)` 检查只读权限；`zN` 约 5008829 进入 `Bi.getIsProjectReadOnly`。它可在写入编译器前返回失败。[官方保存文档](https://prodocs.lceda.cn/cn/api/reference/pro-api.pcb_document.save.html) 规定保存或上传失败均返回 `false`，不能把 `false` 当作正常成功。

这条代码链可同时解释迭代预览期间的保存失败与覆铜创建失败。退出预览后还需单独验证创建、保存、重新打开和磁盘内容，才确认运行故障的实际消除。

### 已排除的配置及面板控制假设

本机菜单使用 `y_e.getConfig(tabId)`，首次直接深复制 `SAn` 默认值；默认 `isDisplay:true`，配置保存在 UI 的 `configs[tabId]` 内存中。设置窗的“应用”才调用 `y_e.saveConfig`。本机没有在该菜单入口把 PCB 文件 `CONFIG` 读取为这些 UI 参数；`openUI('auto-routing')` 也只是打开设置窗，菜单处理没有把调用参数传给设置窗。未找到符合当前接口边界的稳定直接注入入口，不能承诺仅修改新实验 PCB 文件即可关闭迭代展示。

已存在的原生文件自动布线规则形态为记录头与数据之间的 `||` 分隔，记录类别为 `RULE`，标识为 `["RULE","AUTO_ROUTER","Common"]`，数据含 `ruleState` 和 `ruleContext`；当前 `ruleContext` 存储布线角度、保留路线、过孔数量、优先级、图层及忽略网络。它不是上面 UI 内存配置的已证实读入入口。本次没有向它添加假定的 `isDisplay` 字段。

`.logs/tabs-headless-preview.json` 的公开 `getSplitScreenTree` 仅列出开始页与 `PCB1`；这与本机代码一致：迭代面板 `autoRouter` 位于 `right-panel-tab-container`，不是编辑器文档标签。`closeDocument` 只能关闭文档，不能据此关闭迭代面板；`closeRightPanel` 仅收起侧栏，也不解除预览只读。

### 结果捕获与后续兼容适配

`getAutoRouteJsonFile` 的本机实现最终进入 `B1.autoRouting(props,true)`，只生成算法输入数据；`importAutoRouteJsonFile` 遇到包含 `board` 或 `json` 的文件会走输入图形预览路径。两者都是官网标为测试阶段的接口，不能假定它们构成“选中迭代结果导出并应用”的无损闭环。捕获本次结果应使用公开 `PrimitiveLine/Via.getAll` 读取的网络、图层、坐标、线宽及过孔属性。

主代理拟在自有空白试验中验证兼容适配：保存算法结果快照 → 关闭自己的试验会话 → 重新打开同一独立小板 → 核对原始 4 焊盘／0 导线 → 用公开 `PrimitiveLine/Via.create` 按快照写回 → 保存并重新打开验证。该方案不使用私有消息或软件补丁，不删除原始交付，也不修改算法生成的路线含义；它应称“自动应用兼容适配”，不能称专用自动布线接口已经修复。

本追加写入时，结果写回与持久化试验尚未由本子任务读取成功证据；仅描述主代理的下一项验证，不预判成功。
